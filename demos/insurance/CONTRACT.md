# Chhatri Insurance — UI ↔ brain contract

Chhatri Insurance (छतरी, "umbrella") is a **fictional** Indian B2C insurer and a Voqalize voice demo.
It sells car, two-wheeler, health, term life, home and travel insurance. The agent's character
(name, face, voice, languages) lives only in `persona.json` (today: Ananya, `ananya` avatar,
`omnivoice/ananya`, English and Hindi). Nothing else names her: read the file.

This file is the agreement between `frontend/` (React, Vite) and `backend/` (the brain).

## Data (the single source of truth for both sides)

| File | What | Who reads it |
| --- | --- | --- |
| `persona.json` | character id, display names, voice per language, languages offered, default | both |
| `data/products.json` | quote fields, add-ons, rating tables and method, cities/zones | both |
| `data/quote_cases.json` | golden quotes: inputs → breakdown lines + total (generated by `backend/rating.py`) | both test suites |
| `data/claim_form.json` | claim types, sections, fields, `show_if`, documents, declaration | both |
| `data/customer.json` | the signed-in customer (one), family, bank on file, policy ids, past claims | both |
| `data/policies/<policy_id>.json` | each policy's full document (schedule + sections + clauses) | both |
| `data/network.json` | network garages and hospitals (fictional, Pune and around) | both |
| `content/products.json` | product page copy: hero, highlights, covered / not covered, add-on explainers, FAQs | page (brain: the add-on explainers and FAQs) |
| `content/claims_guide.json` | what happens after a claim is submitted, per type; claim helpline | both |

**No invented facts.** Ananya states only what these files say: a premium comes from the rating
engine, a coverage answer from a clause, a next step from the claims guide. Everything is clearly
fictional: no real insurers, banks, hospitals, garages, car makes, people or registration numbers.

## Routes and landings

`BASE = /demos/insurance/`. Each agent job has a landing; the page sends its path in `init`.

| Route | Page | Brain mode |
| --- | --- | --- |
| `/` | home | `home` (routes to a job) |
| `/insurance/<product>` | product page, with the quote builder embedded | `quote` |
| `/quote`, `/quote/<product>` | quote builder (product tabs + form + live breakdown) | `quote` |
| `/my-policies` | signed-in dashboard: the customer's policies, renewals, past claims | `policies` |
| `/my-policies/<policy_id>` | the policy document viewer (TOC + sections + clauses) | `policies` |
| `/claim` | claim type chooser + the long multi-section claim form, ending in Review | `claim` |
| `/claim/submitted` | confirmation with the claim reference | `claim` |

The brain follows the visitor: every route change sends Stage's `hello` with the path, and the brain
switches job (`home | quote | policies | claim`) from it.

## Connect request `init`

`{ "surface": "insurance-web", "landing": "/quote/car", "lang": "en" | "hi" }` — `lang` is the
EN / हिंदी toggle by the call button (default `persona.default_language`). The brain configures
both speech legs from it in `on_session_start`. The page never sends voice or language config.

## Stage (the only way the agent changes the screen)

Spec: `frontend/src/stage/scene.json` → `voqalize stage gen … --py backend/stage_gen.py --ts
frontend/src/stage/scene.gen.ts`. Every move is tool-sent (`stage.send`, no cues). Every performer
rings its target before it acts, refuses with the options the page offers, and returns one short
line. Every move also works by click: performers call the same store actions the controls do.

| Move | Args | Page does |
| --- | --- | --- |
| `site.go` | `page` | navigate (home, quote, quote/<p>, insurance/<p>, my-policies, my-policies/<id>, claim) |
| `site.language` | `language` en\|hi | moves the toggle |
| `quote.open` | `product` | builder for that product on screen |
| `quote.fill` | `field, value` | ring field, set it, premium recomputes |
| `quote.addon` | `addon, on` | ring toggle, switch; refused when unavailable (with why) |
| `quote.show` | — | ring the breakdown panel |
| `policy.open` | `policy_id, section?` | open the document |
| `policy.mark` | `policy_id, clause_id, verdict` | scroll, ring, highlight clause, verdict chip |
| `claim.start` | `claim_type, policy_id?` | /claim with type (and policy) chosen |
| `claim.fill` | `field, value` | open section, ring, set |
| `claim.section` | `section` | open + ring section |
| `claim.review` | — | validate all, open review, refused naming missing fields |

Nothing submits: the customer ticks the declaration and presses **Submit claim**; uploads are the
customer's (mock: the file picker or "Use sample file", a short progress bar, then the file name).

### Events (page → brain, Stage state events; `by` from `moves.author()`)

- `quote.changed` (set): `{product, field, answers[{field,value}], addons[], missing[], total?}` — every
  change to the quote builder, by the visitor or by a move.
- `policy.viewed` (set): `{policy_id, section?}`.
- `claim.changed` (merge): `{claim_type, policy_id, section, field, filled[], missing[]}` — names only, never values.
- `claim.document_uploaded` (merge): `{field: <document id>, documents[]}`.
- `claim.submitted` (merge): `{reference, filled[], documents[]}` — the brain thanks and says the next step.
- `site.language_chosen` (set): `{language}` — the toggle moved mid-call; the brain moves both legs.

## Rating

`data/products.json` `method` lines are normative. `backend/rating.py` and
`frontend/src/quote/rating.ts` implement them identically; `data/quote_cases.json` is generated by
`uv run python -m insurance.backend.rating --cases` (from `demos/`) and both test suites check it.
Breakdown line shape: `{ "id", "label", "amount" }` (discounts negative), then `net`, `gst`, `total`.

## Redial: a call outlives a dropped brain socket (owner, 2026-11-23)

SDK 0.15.0 `Config.redial`, the same pattern as Fernhollow (its CONTRACT.md v7). On a Voqalize that
offers redial (`session.can_redial`), `on_session_start` turns it on in the same `configure` as the
persona's voice and both speech legs. Each live brain is kept in this process by session id
(`backend/rejoin.py`) while its socket is up and for two minutes after it drops. A redial that reaches
the same process (a Cortex restart, a network blip) adopts the call as it was: the job, page and
product on screen, the language it had moved to (not the init's), the quote answers and add-ons per
product, the claim (type, policy, values, documents, what the page reported filled and missing,
reference), the marked clause, the model's history, the Stage director that knows the page, and any
line or ask queued for the next quiet spell. It sends no second greeting and no second start note to
the model. The demo's data files are read-only, so the call changes nothing outside the brain. A
redial that reaches a fresh process, or comes after the two minutes, starts a new conversation from
the init's page and language. No page change: the page sees the same session throughout.

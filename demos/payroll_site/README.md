# Paynora — the marketing site (`payroll_site`)

Paynora is a fictional Indian HR and payroll product for companies of 20 to 1,000 people. This
demo is its marketing website, with a voice sales agent who talks to the visitor and drives the
screen while he talks: he fills a lead card field by field, sets the pricing calculator control by
control, and picks a slot on the sales calendar. Its sibling, `payroll_app`, is the product itself;
both read the same `data/product.json`.

Every company, person and number is invented. Tax figures follow FY 2025-26 and are labelled
illustrative.

## Pages

| Route | What is on it |
| --- | --- |
| `/` | Hero, pain points, the module grid, the tax showcase, customer quotes, the lead card |
| `/modules`, `/modules/<id>` | All ten modules, and a page per module |
| `/tax` | FY 2025-26 slabs for both regimes, standard deduction, 87A, 80C/80D/80CCD(1B)/HRA/LTA/24(b), PF/ESI/PT, TDS and Form 16, and the worked old-vs-new example from `data/tax_example.json` |
| `/customers` | The five customers |
| `/pricing` | Plans, the calculator with its line-by-line breakdown, notes, FAQ |
| `/book-demo` | The sales calendar (next 10 business days, IST), the booking form, the confirmation |

## One agent, three jobs

The page the call starts on picks the job (`init.page`), and the brain follows the visitor when
they move (Stage's `screen.viewed`).

- **Sales rep** (`/` and the product pages): asks about headcount, the current payroll tool, the
  states they operate in and what hurts; every answer goes on the lead card (`lead.fill`, one
  field at a time), and the modules that fit are ringed and marked (`modules.highlight`). The
  suggested plan comes from the pricing rule. An email goes on the card only once it was read back
  and confirmed. Then he hands off to pricing or a demo.
- **Pricing explainer** (`/pricing`): works out the plan from `pricing_rules.plan_choice`, sets
  the calculator (`pricing.set`: headcount, each module, billing, the filing add-on, each ringed),
  and talks the maths through with `{line: …}` cues: headcount × rate, whether the minimum
  applies, the add-on, the annual discount, GST, the setup fee.
- **Demo booker** (`/book-demo`): shows a day's free slots (`calendar.show`), picks one
  (`booking.pick`), fills the form (`booking.fill`), and confirms (`booking.confirm`) only after the
  visitor's spoken yes in a later turn.

Everything also works by click alone: clicks, the agent's moves and the `?debug=1` console all go
through one store controller (`frontend/src/state/store.ts`). `?debug=1` fires any move by hand,
runs each agent's main flow as a script, and fakes a live call for screenshots.

The contract between the two halves is `CONTRACT.md`; the moves are `frontend/src/stage/scene.json`.

## Facts the agent may state

Only what is in `data/product.json`, `data/tax_example.json` and `content/site.json`. Pricing is one
function on each side (`backend/pricing.py`, `frontend/src/lib/pricing.ts`), and the calendar too
(`backend/calendar_rules.py`, `frontend/src/lib/calendar.ts`); `content/pricing_cases.json` and
`content/calendar_cases.json` hold both twins to the same numbers. For example, 56 employees who
need reimbursements are on Growth at ₹6,664 a month before GST.

`data/product.json` and `data/tax_example.json` are generated by `payroll_app/data/build_data.py`;
do not edit them here. Site-only copy goes in `content/site.json`.

## Run it

```sh
# The brain, with the other demos
cd demos && uv run uvicorn voqalize_demos.umbrella:app --reload --port 8080   # or pm2, see demos/README.md

# The site (standalone; the dev port is given on the command line)
cd demos/payroll_site/frontend
pnpm install --ignore-workspace
cp .env.example .env    # VITE_AGENT_ID and VITE_PUBLISHABLE_KEY for a call
pnpm dev --port 5402    # http://localhost:5402/demos/payroll_site/  (?debug=1 for the console)
```

Without `.env` the site works fully by hand and the dock says voice is off.

Tests and checks:

```sh
cd demos && uv run pytest tests/test_payroll_site_e2e.py tests/test_demo_voice_contract.py -q -k payroll_site
cd demos/payroll_site/frontend && pnpm typecheck && pnpm test && pnpm build
uv run voqalize stage gen payroll_site/frontend/src/stage/scene.json \
  --py payroll_site/backend/stage_gen.py --ts payroll_site/frontend/src/stage/scene.gen.ts   # after editing scene.json, from demos/
```

## A dropped socket does not end the call

Where Voqalize offers redial, the brain turns it on. If its socket drops without a hang-up (a
restart, a network blip), Voqalize dials it again for the same session and the new brain picks up
the call from `backend/rejoin.py`: same job, language, lead card, held slot and model history, no
second greeting. Calls are held in process memory for two minutes after the drop, so a redial that
reaches a freshly deployed process starts over. See `CONTRACT.md`, Redial.

## Change the character or add a language

The character lives in one file, `persona.json`: the avatar character, the display name, the role,
a voice per language, the languages offered (code, label, toggle text) and the default. The brain
(`backend/persona.py`) and the page (`frontend/src/persona.ts`) both read it; the greeting, the
"Talk to …" button, the toggle and the tests take the name from there. `roles` holds the dock's
label per job (sales, pricing, demo booking), picked by the page the visitor is on.

- **Another character**: change `avatar_character`, `display_name` and `voices` to a character
  and a voice from the catalogue (`GET /api/v1/catalog.get`) whose voice speaks every listed
  language.
- **Another language**: add it to `languages` and `voices`, then add its row to every table in
  `backend/lines.py` (the brain refuses to start without them). The brain moves both speech legs
  (recognizer and voice) together, at the start and when the visitor switches mid-call.
